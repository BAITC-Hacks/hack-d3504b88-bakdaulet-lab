# Сценарий демонстрации

## Live: фактическая проверка 23.09.2026 после объединения веток

1. В локальном `.env` задайте EKT/OpenAI-секреты, `OPENAI_MODEL=gpt-6-sol`, `DATA_MODE=live`. Запустите `npm run catalog:sync`, затем `npm run dev`. Проверьте `/api/health`: режим `live`, число проиндексированных товаров и готовность.
2. В чате введите `310100086_`. Карточка EKT `18157` показала нулевой остаток. Под ней найден кандидат `515262` (`200300265_`): при проверке было 74 шт. Совпали 3 полюса, 20 А, 400 В, 4,5 кА, характеристика C. Покажите предупреждение о непроверенной монтажной совместимости и ссылки на обе карточки EKT.
3. Спросите «Условия доставки в Алматы». Ответ должен содержать ссылку на [официальную страницу EKT](https://ekt.kz/about/information/).
4. Нажмите «Предложить 1 шт.» у аналога. Откройте `/cart` до подтверждения: корзина пуста. Вернитесь в чат, подтвердите предложение и откройте корзину; после обновления страницы позиция остаётся.
5. Повторный запрос подтверждения не дублирует количество. Запрос сверх актуального остатка отклоняется сервером. Для автоматической проверки используйте `npm run smoke:live` и `npm run browser:live`.
6. При необходимости покажите расхождение у `515291`: название говорит 160 А, свойство API — 250 А. Такая карточка не считается подтверждённой заменой.

После объединения веток прошли `npm run live:check`, `npm run smoke:live` и `npm run browser:live`: EKT вернул страницу из 20 товаров и detail ID 45357, health показал 500 карточек и готовность, пара `18157` → `515262` снова имела остатки 0 → 74 шт. OpenAI `gpt-6-sol` выполнил реальный вызов функции; браузерный сценарий прошёл на desktop и 390 px mobile с обновлением корзины. Перед защитой повторите `npm run live:check` и `npm run analogs:discover`: цены, остатки и даже выбранная пара могут измениться. Частичный индекс не описывает весь ассортимент. Скриншоты live-прохода находятся в `screenshot-live-desktop.png` и `screenshot-live-mobile.png`. Ссылку на сертификат для выбранной пары не обещайте: ограниченная проверка 23 реальных карточек не подтвердила применимый документ.

## Demo без внешних ключей

При `DATA_MODE=demo` используйте `DEMO-AV16-OLD` → `DEMO-AV16`. После предложения и подтверждения проверьте `/cart`. Синтетические цены и остатки не относятся к магазину. Демо-проверки: `node scripts/smoke-http.mjs` и `node scripts/check-browser.mjs`.

## Demo загрузки спецификации

1. В новой cookie-сессии с пустой корзиной и `DATA_MODE=demo` загрузите [review.xlsx](../tests/fixtures/ocr/review.xlsx). Это синтетический файл.
2. Покажите три строки черновика. У первой `DEMO-AV16 / 2 / шт`; отметьте её «Проверено». У второй `DEMO-AV25` заполните количество `1` и единицу `шт`, затем отметьте «Проверено». Третья строка с неизвестным артикулом и `упак` остаётся видимой, но исключённой.
3. Покажите сводку «2 из 3» и пустую корзину. Нажмите «Подготовить предложение из проверенных строк», проверьте состав и снова покажите, что корзина не изменилась до отдельного подтверждения. Только после явного согласия подтвердите добавление и откройте `/cart`.

В ветке OCR три вызова настоящего OpenAI API на синтетических `specification.jpg`, растровом `scan.pdf` и неясном `unclear.jpg` прошли; фото клиента не проверялось. Не представляйте эти файлы как реальные документы покупателя. После интеграции браузерный demo-сценарий с отдельной БД подтвердил на desktop и mobile ровно две отмеченные строки, отдельное подтверждение добавления и сохранение корзины после refresh. Новых платных OCR-вызовов не было. Docker Compose прошёл статическую проверку, но контейнерный показ требует доступного Docker Engine и проверки сборки/запуска.

На защите прямо сообщите: каталог в live читается из API партнёра; корзина прототипа собственная, так как API корзины не выдан. Приложение не резервирует товар и не оформляет заказ на ekt.kz.
